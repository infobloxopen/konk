## ISSUE-1 — etcd server certificate SANs do not cover the etcd members

**Found:** 2026-09-01, on us-dev-2, immediately after the 1 → 3 member migration
**Component:** konk — `helm-charts/konk/scripts/provision.sh`
**Severity:** low urgency / real latent risk — no production traffic affected today
**Status:** open

### Summary

The etcd server certificate is generated by the **provision (init) pod** using
`kubeadm`, and its SAN list names the *init pod* rather than the *etcd members*.
It contains no per-member FQDN and no fully-qualified form of the headless
service. This was survivable when etcd ran a single pod; with three members it
silently blocks standard per-member etcd tooling.

### Evidence (verified 2026-09-01)

Live secret `aggregate/bulk-konk-etcd-cert`:

```
subject=CN=bulk-konk-init-7df4dcb778-pg28j
notBefore=Jul  9 11:34:19 2026 GMT
notAfter =Sep  1 09:52:25 2027 GMT
X509v3 Subject Alternative Name:
    DNS:bulk-konk-etcd-headless,
    DNS:bulk-konk-init-7df4dcb778-pg28j,
    DNS:localhost,
    IP Address:100.64.75.65,
    IP Address:127.0.0.1,
    IP Address:0:0:0:0:0:0:0:1
```

Current etcd members — the SAN IP matches **none** of them:

| Pod | IP |
|---|---|
| `bulk-konk-etcd-0` | `100.64.36.218` |
| `bulk-konk-etcd-1` | `100.64.81.10` |
| `bulk-konk-etcd-2` | `100.64.166.195` |

`bulk-konk-init-7df4dcb778-pg28j` is a **dead pod**; the current init pod is
`bulk-konk-init-8f48677c5-wzbdv`. The secret has no cert-manager `Certificate`
behind it — it is created and patched directly by `provision.sh` and owned by the
`bulk-konk` Deployment.

### Why nothing is broken today

The TLS surface is narrower than it appears:

| Port | URL | TLS |
|---|---|---|
| 2379 client | `https://0.0.0.0:2379` | **yes** — `ETCD_CLIENT_CERT_AUTH=true` |
| 2380 peer | `http://0.0.0.0:2380` | **no** |
| 2381 metrics | `http://0.0.0.0:2381` | **no** |

- **Peer/raft traffic is plain HTTP**, so the cert is irrelevant to cluster
  formation. This is why the 3-member cluster came up cleanly.
- **Metrics are plain HTTP**, so PodMonitor scraping is unaffected.
- The only real client is the konk apiserver, and it uses the one name that *is*
  in the SAN:

  ```
  --etcd-servers=https://bulk-konk-etcd-headless:2379
  ```

  Go verifies against the hostname in the URL, not the resolved IP, so it works
  regardless of which member it reaches.

### What is actually broken

**etcd advertises a client endpoint that fails its own certificate.**

```
ETCD_ADVERTISE_CLIENT_URLS=https://$(ETCD_NAME).bulk-konk-etcd-headless.aggregate.svc.cluster.local:2379
```

That per-pod FQDN is not in the SAN. Anything that discovers members through the
membership API and connects to the advertised URL fails verification:

```
x509: certificate is valid for bulk-konk-etcd-headless,
bulk-konk-init-7df4dcb778-pg28j, localhost,
not bulk-konk-etcd-0.bulk-konk-etcd-headless.aggregate.svc.cluster.local
```

Concrete consequences:

- **Cluster-wide `etcdctl` is impossible.** `endpoint status` / `endpoint health`
  across all three members from one place fails on all three. The only working
  path is `kubectl exec` into *each* pod and target `localhost`.
- **Any client with etcd endpoint auto-sync enabled** breaks the moment it is
  turned on.
- **Connecting by pod IP** fails for every member.
- Backup / restore / DR tooling conventionally targets per-member endpoints —
  that would fail.
- If peer traffic were ever moved to TLS it would fail outright, since the cert
  carries no member identity at all.

### Root cause

`helm-charts/konk/scripts/provision.sh` (~lines 28–40):

```bash
cat << EOF > /tmp/kubeadmcfg.yaml
apiVersion: "kubeadm.k8s.io/v1beta2"
kind: ClusterConfiguration
etcd:
  local:
    serverCertSANs:
    - localhost
    - $RELEASE-etcd-headless        # short name only
EOF

kubeadm init phase certs all --apiserver-cert-extra-sans $FULLNAME,$FULLNAME.$NAMESPACE,$FULLNAME.$NAMESPACE.svc,$FULLNAME.$NAMESPACE.svc.cluster.local
rm -f /etc/kubernetes/pki/etcd/server*
kubeadm init phase certs etcd-server --config=/tmp/kubeadmcfg.yaml
```

Two things combine:

1. **Only two SANs are declared** — `localhost` and the **short** headless service
   name. No `.NAMESPACE`, `.NAMESPACE.svc`, `.NAMESPACE.svc.cluster.local`, and no
   per-member name. Note the apiserver cert on the line above *does* get the full
   ladder via `--apiserver-cert-extra-sans`; the etcd cert never got equivalent
   treatment.
2. **kubeadm treats the init pod as "the node"**, so it adds the container
   hostname (the init pod name) as CN and SAN, plus the init pod's IP. Those are
   meaningless to etcd and change on every rollout.

Confirmed from the current init pod's own log:

```
[certs] etcd/server serving cert is signed for DNS names
        [bulk-konk-etcd-headless bulk-konk-init-8f48677c5-wzbdv localhost]
        and IPs [100.64.122.156 127.0.0.1 ::1]
```

`100.64.122.156` is the **init pod's** IP — not any etcd member's.

### ⚠️ Secondary open question — the secret does not match what provision generated

`provision.sh` ran today at ~09:52 in pod `bulk-konk-init-8f48677c5-wzbdv`,
generated a cert naming that pod, and the log reports the patch succeeded:

```
+ kubeadm init phase certs etcd-server --config=/tmp/kubeadmcfg.yaml
[certs] etcd/server serving cert is signed for DNS names [bulk-konk-etcd-headless bulk-konk-init-8f48677c5-wzbdv localhost] ...
+ kubectl -n aggregate patch secret bulk-konk-etcd-cert --type=json -p '[...]'
secret/bulk-konk-etcd-cert patched
```

But the live secret still serves the **July 9** cert naming the *old* init pod —
while its `notAfter` (`Sep 1 09:52:25 2027`) lands exactly one year after today's
provision run. So the validity window appears to have moved without the CN/SAN
changing.

Worth resolving as part of the fix, because it means **regenerating the cert may
not actually replace what etcd serves**. To investigate:

```bash
CTX=teleport.services.sdp.infoblox.com-us-dev-2

# full provision log, in order
kubectl --context $CTX logs -n aggregate deploy/bulk-konk-init --all-containers --tail=-1 \
  | grep -nE 'etcd-server|serving cert|patch secret|etcd-cert'

# is /etc/kubernetes/pki/etcd a writable emptyDir, or a read-only secret mount?
kubectl --context $CTX get deploy bulk-konk-init -n aggregate \
  -o jsonpath='{.spec.template.spec.containers[0].volumeMounts}{"\n"}'

# does what etcd actually serves match the secret?
kubectl --context $CTX exec -n aggregate bulk-konk-etcd-0 -- \
  cat /etc/etcd/certs/client/server.crt | openssl x509 -noout -subject -dates -ext subjectAltName
```

> Note: the etcd image is distroless, so `cat` inside the pod may not work — use
> `kubectl debug` with a shell image, or compare the mounted secret's
> `resourceVersion` against the pod start time instead.

### Proposed fix

Declare the SANs etcd actually needs, and stop depending on the init pod's
identity. In `provision.sh`:

```yaml
etcd:
  local:
    serverCertSANs:
    - localhost
    - 127.0.0.1
    - $RELEASE-etcd
    - $RELEASE-etcd.$NAMESPACE
    - $RELEASE-etcd.$NAMESPACE.svc
    - $RELEASE-etcd.$NAMESPACE.svc.cluster.local
    - $RELEASE-etcd-headless
    - $RELEASE-etcd-headless.$NAMESPACE
    - $RELEASE-etcd-headless.$NAMESPACE.svc
    - $RELEASE-etcd-headless.$NAMESPACE.svc.cluster.local
    - "*.$RELEASE-etcd-headless.$NAMESPACE.svc.cluster.local"   # per-member FQDNs
```

Notes:

- The wildcard covers `bulk-konk-etcd-N.bulk-konk-etcd-headless.aggregate.svc.cluster.local`
  for any replica count, which is what `ETCD_ADVERTISE_CLIENT_URLS` publishes.
  If wildcards are unacceptable, enumerate members from
  `statefulset.replicaCount` instead — but then the cert must be regenerated on
  every scale change.
- **Do not add pod IPs.** They change on every reschedule; that is exactly how the
  current stale `100.64.75.65` got in.
- The init pod hostname/IP land in the cert as a kubeadm side effect. Harmless if
  the real names are present, but cleaner to suppress if kubeadm allows it.
- Longer term, moving this cert to **cert-manager** would remove the
  per-provision-pod coupling entirely and give proper rotation. The konk-service
  chart already uses cert-manager `Certificate` resources
  (`helm-charts/konk-service/templates/certificate.yaml`), so there is precedent.

### How to verify a fix

```bash
# 1. SANs cover the members
kubectl -n aggregate get secret bulk-konk-etcd-cert -o jsonpath='{.data.server\.crt}' \
  | base64 -d | openssl x509 -noout -ext subjectAltName

# 2. per-member TLS works from a single client (currently fails)
kubectl -n aggregate exec bulk-konk-etcd-0 -- etcdctl \
  --cacert=/etc/etcd/certs/client/ca.crt \
  --cert=/etc/etcd/certs/client/server.crt \
  --key=/etc/etcd/certs/client/server.key \
  --endpoints=https://bulk-konk-etcd-0.bulk-konk-etcd-headless.aggregate.svc.cluster.local:2379,https://bulk-konk-etcd-1.bulk-konk-etcd-headless.aggregate.svc.cluster.local:2379,https://bulk-konk-etcd-2.bulk-konk-etcd-headless.aggregate.svc.cluster.local:2379 \
  endpoint status -w table

# 3. no SAN references a pod that no longer exists
```

A check for this is proposed as section 19 of `tests/post-upgrade.sh` — assert the
SAN covers the headless service name plus member FQDNs, and warn when the CN or
any SAN names a non-existent pod.
